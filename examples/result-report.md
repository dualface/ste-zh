# 範例：結果回報

本範例的來源是虛構的。

## Agent 掌握的事實

改寫只改寫法，不增加事實（R25）。改寫後的每個事實都來自本節。

- 使用者的要求：修復登入後偶發退出的問題。使用者沒有要求改日誌和重試邏輯。
- Agent 讀了 `auth/refresh.ts`。第 42 行在更新前不檢查是否已有更新在進行。
- 兩個請求同時更新 token 時，後完成的更新使先拿到的 token 失效。
- Agent 修改了 `auth/refresh.ts`：同一時間只發一個更新請求，其他請求等待這次更新的結果。
- Agent 刪除了 `auth/logger.ts` 中的 3 處重複日誌。
- Agent 新增了併發更新測試，位置是 `auth/refresh.test.ts:88`。
- `npm test auth` 的輸出：48 項通過，0 項失敗。新增的測試在其中。
- 本機沒有 iOS 建置環境。

## 改寫前

> 好的，我先看了一下登入相關的程式碼，發現問題應該是出在 token 更新的邏輯上，大概是併發的時候兩個請求同時去更新導致的。然後我對 `auth/refresh.ts` 進行了修改，加了一個鎖來實現序列化處理，另外順手把一些日誌之類的也優化了一下。測試基本都跑過了，應該沒什麼問題，不過 iOS 那邊因為沒有環境暫時沒法驗證。你看要不要我再把重試邏輯也一起改了？

不合格的地方：

- 第一句不是結論（R18）。
- 敘述過程：「我先……然後……」（R21）。
- 「應該」「大概」掩蓋不確定（R24）。
- 「進行了修改」「實現序列化處理」是虛化動詞（R3）。
- 「日誌之類」是開放式列舉（R17）。改動也超出了範圍。
- 「基本都跑過了」不是固定狀態詞，沒有寫出檢查方法（R19、R20）。
- 最後的問題沒有編號選項（R23）。

## 改寫後

已完成：修復登入後偶發退出的問題。iOS 端未驗證。

**原因**：兩個請求同時更新 token。後完成的更新使先拿到的 token 失效。

**證據**：
- `auth/refresh.ts:42` — 更新前不檢查是否已有更新在進行。

**改動**
- `auth/refresh.ts`：同一時間只發一個更新請求。其他請求等待這次更新的結果。
- `auth/logger.ts`：刪除 3 處重複日誌。這項改動不在原範圍內。

**驗證**
- 已驗證：`npm test auth` — 48 項通過，0 項失敗。
- 已驗證：新增併發更新測試 `auth/refresh.test.ts:88` — 通過。
- 未驗證：iOS 端 — 本機沒有 iOS 建置環境。

**待確認**
- 是否保留 `auth/logger.ts` 的改動：
  1. 撤回（推薦）— 本次提交只含登入修復。
  2. 保留 — 日誌清理和登入修復一起提交。

## 說明

- 本範例合併了兩個模板：結果回報加入了排查結論的「原因」節和「證據」節。
- 改寫前的「測試基本都跑過了」沒有寫出檢查方法。改寫後的數字來自「Agent 掌握的事實」，不是改寫時補充的。Agent 沒有這些事實時，必須寫「未驗證」。
- 「重試邏輯」只是 Agent 的提問，使用者沒有要求。改寫後刪除了這個問題，避免擴大範圍。
- 超出範圍的改動必須在「改動」中標明，並讓使用者決定。
